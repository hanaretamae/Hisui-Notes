# ADR-0008: 共通権限モデル

- **Status:** 採用（Accepted）
- **日付:** 2026-11-08
- **関連:** 統合開発計画 §2.2（権限管理）、§11.5、§12.4、§14.3、§15.2、§19.1、§20.3／実行計画 D-10
- **優先順位:** プライバシーとセキュリティを性能より優先する。そのうえで、権限検査が編集・描画の性能目標（[`requirements/non-functional.md`](../requirements/non-functional.md)）を損なわない実装方式を定める。

## Context

統合開発計画では、次の要素がそれぞれ権限を持つと定めている。

- ユーザープラグイン・パーサーのCapability宣言（§3.3、§19.1）
- MCP Serverごとのアクセス可能なVault・文書、外部ツール実行の確認（§11.5）
- ACP Agentのセッションごとの権限、書き込み・削除の確認（§12.4）
- UIモジュール・ボタンの「必要な権限」（§14.3、§15.2）
- AIプロバイダー、外部連携の接続先ごとの権限（§20.3）

これらを個別に実装すると、同じ操作（例: 文書の書き込み）の許可が経路ごとに異なり、利用者が権限を一か所で確認・取り消しできず、確認の基準が揃わない。

## Decision

`app-core` に単一の権限基盤（Permission Broker）を置き、すべての拡張体系とプロトコル連携がこれを経由する。

### 1. 主体（Principal）

| 種類 | 例 | 権限の単位 |
|---|---|---|
| `extension` | ユーザープラグイン、パーサー、テーマ、言語拡張 | 拡張ID。付与時のバージョンを記録する |
| `mcp-server` | 登録済みMCP Server | サーバー登録ID |
| `acp-agent` | 登録済みACP Agent | Agent登録ID。セッションIDで細分化する |
| `ai-provider` | AIプロバイダー | プロバイダー登録ID |
| `core` | アプリケーション本体、コアプラグイン | 本体は暗黙に許可する。コアプラグインは拡張と同じく権限を宣言し、`external` 区分の権限は付与を要する |

- UIモジュールとボタンは独立した主体にせず、登録した主体の権限を継承する。
- 主体を偽装できないようにする。主体IDはホストが接続・読み込みの時点で割り当て、拡張や相手側から申告させない。

### 2. 権限（Capability）

権限は「名前」と「範囲（Scope）」の組で表す。

- 名前は名前空間付きの識別子とする。コアが基本権限を定義し、各拡張体系は自分の名前空間に権限を追加登録できる。他の名前空間には登録できない。
- 各権限にリスク区分を付ける。

| 区分 | 意味 | 例 |
|---|---|---|
| `read` | Vault内の情報を読む | `vault.read`、`vault.list`、`document.read-metadata` |
| `write` | 既存の情報を変更する | `vault.write`、`document.edit` |
| `destructive` | 削除・上書き・取り消しにくい変更 | `vault.delete`、`vault.move`、`vault.overwrite` |
| `external` | アプリの外へ情報を出す、外部の実行環境を使う | `net.connect`、`process.spawn`、`ai.send-content`、`clipboard.write` |
| `sensitive` | 秘密情報や利用者の私的な情報に触れる | `secret.use`、`secret.read-own`、`clipboard.read`、`location` 等 |

範囲の表現:

| 対象 | 形式 | 規則 |
|---|---|---|
| Vault・文書 | Vault ID + Vault相対パスの接頭辞、またはglob | パスは正規化してから照合する。`..`、絶対パス、シンボリックリンク経由でVault外を指すパスは範囲外として拒否する。大文字・小文字の扱いはファイルシステムに合わせる |
| ネットワーク | スキーム + ホスト + ポートの完全一致（オリジン） | ワイルドカードは利用者が明示したサブドメインのみ。`http` はループバックアドレスに限る |
| プロセス | 実行ファイルの絶対パス + ハッシュ | 実行ファイルが変わった場合は再確認する |
| シークレット | シークレットのキー | 主体ごとに分離する |

### 3. 宣言と付与

- 拡張はマニフェストで必須権限と任意権限を宣言する。MCP Server・ACP Agent・AIプロバイダーは登録時に権限を設定する。
- **既定は拒否とする。** 宣言していない権限は付与できない。インストール・登録だけでは何も付与しない。
- 付与は利用者が行う。有効期間は「1回限り」「セッション中」「永続」、適用範囲は「Vault」「ワークスペース」「全体」とする。**既定の適用範囲はVault**とし、「全体」は明示的に選んだ場合のみとする。
- 付与情報は設定とは別のストアに保存する。一覧・取り消しのUIを提供する。
- 拡張の更新で必須権限が増えた場合、その拡張を無効化し、追加分の付与を求める。任意権限の追加分は付与しない。権限が減った場合は不要になった付与を削除する。
- 付与から90日間使われなかった永続付与は失効させる（`destructive`、`external`、`sensitive` 区分のみ）。

### 4. 確認

- `destructive` と `external` の操作は、永続付与があっても操作ごとに確認する。
  - 利用者は権限ごとに確認を省略できる。ただし、省略を設定できる範囲はVault単位までとし、「全体」では省略できない。
  - `ai.send-content` のうち、リモートのAIプロバイダー（ループバック以外への送信）は確認を省略できない。会話ごとに、送信する文書・範囲を表示して確認する。同じ会話で同じ文書の再送信は、内容が変わっていなければ確認しない。
- 確認UIは単一の仕組み（Command Surface）とし、主体・操作・対象・送信先を表示する。確認文言を主体側から指定させない（偽装防止）。
- 確認UIを表示できない状態（バックグラウンド、ヘッドレス、画面ロック中）で確認が必要になった操作は拒否する。
- 確認が短時間に続く場合は、同じ主体・同じ権限の要求をまとめて一度に確認する。まとめても対象の一覧は省略しない。

### 5. 強制

- 保護対象（ファイル、ネットワーク、プロセス、シークレット、クリップボード、文書編集）へのアクセスはホストサービス経由に限る。WASM拡張には直接のアクセス手段（WASIのファイルシステム・ソケットを含む）を与えない。
- ホストサービスは `check(主体, 権限, 範囲)` を呼び、結果 `Allow`・`Deny`・`Confirm` に従う。判定できない場合（範囲の解析失敗、内部エラー）は `Deny` とする。
- MCP・ACPの接続モジュールは、相手側からの要求（ACP Agentのファイル読み書き要求、MCPのSampling・Elicitation・Roots要求など）を同じ方法で検査する。
- ACPのセッション権限は、Agentに付与された権限との積集合とする。セッション側でAgentの権限を超えることはできない。
- 取り消しは即時に反映する。実行中のセッションの後続操作は拒否される。

### 6. シークレット

同じシークレット管理の仕組みを、本体の機能（AIプロバイダー、MCP・ACPの認証）と、拡張が独自に必要とするシークレット（拡張が連携する外部サービスのAPIキーなど）の両方に使う。拡張が独自の保存方法を実装しなくて済むようにする。

- **保存先:** Platform層のセキュアストレージ（各OSのキーチェーン等）に保存する。設定ファイル、Vault、拡張のデータ領域には保存しない。
- **名前空間:** シークレットは主体ごとの名前空間に置く（例: `extension:<拡張ID>/<キー>`、`mcp-server:<登録ID>/<キー>`）。主体は自分の名前空間のシークレットだけを扱える。他の主体の名前空間には、どの権限でもアクセスできない。
- **宣言:** 拡張はマニフェストで使用するシークレットのキーと用途の説明を宣言する。値の入力は、ホストの入力UIから利用者が行う。拡張のUIで値を受け取らせない（拡張側に値が残らないようにするため）。
- **使用（`secret.use`、`sensitive`）:** 既定の使い方とする。ホストがシークレットを使って処理を行い、値は拡張に渡さない。例: ホストのHTTPサービスが、許可された接続先（ADR-0008 §2のネットワーク範囲）への要求に限って認証ヘッダーを付与する。シークレットごとに、使用できる接続先を宣言・付与時に固定する。
- **値の読み取り（`secret.read-own`、`sensitive`）:** HTTPの認証ヘッダー以外の方式（署名の計算など）で値そのものが必要な拡張に限り、自分の名前空間のシークレットの値を読める。付与時に、値が拡張に渡ることを明示して確認する。読み取った値は拡張のメモリ内でのみ扱う。ホストのストレージAPIやログAPIに渡された値は拒否・マスクする。
- **削除:** 拡張をアンインストールすると、その拡張の名前空間のシークレットを削除する。削除前に利用者に通知する。
- **出力の禁止:** シークレットの値を、ログ、エラーメッセージ、診断情報、監査ログ、AIへの送信内容、エクスポート、同期データに含めない。
- **MCP Server・ACP Agent:** 値を渡す必要がある接続方式（stdioで起動するサーバーの環境変数など）では、起動時にホストが渡す。登録時に、どのシークレットをどの環境変数で渡すかを利用者が確認する。

### 7. OSの権限との関係

OSの権限（Androidのストレージアクセス、iOSのファイルアクセスなど）はPlatform層が管理する。Permission Brokerがアプリ内で許可しても、OS側で利用できない場合は拒否する。

### 8. 記録

- 許可・拒否・確認の結果を監査ログに記録する。
- 監査ログに文書内容、シークレット、送信内容を含めない。パスはVault相対パスで記録する。
- 監査ログは端末内にのみ保存し、外部へ送信しない。保存期間は既定30日とし、利用者が変更・削除できる。
- `read` 区分の許可は、主体・権限・範囲ごとの回数に集約して記録する。`write` 以上は操作ごとに記録する。

### 9. 性能上の実装方針

権限検査は文書読み込み・編集・パーサー呼び出しの経路に入るため、次の方式で検査の負荷を抑える。いずれもセキュリティ上の判定結果を変えないことを条件とする。

- **付与表のメモリ保持:** 付与情報は起動時とその変更時に、主体ごとの判定表へ変換してメモリに保持する。`check` はディスクI/Oやロック待ちを伴わない。
- **ハンドル方式:** ファイルや接続は、開く時点で権限を検査し、ハンドルを発行する。以後の読み書きはハンドルに記録された権限で判定し、毎回の範囲照合を行わない。
- **世代番号による失効:** 付与表に世代番号を持たせ、取り消し・変更のたびに更新する。ハンドルは操作のたびに世代番号を比較し（アトミック読み取り1回）、一致しなければ再検査する。これにより取り消しの即時反映とハンドル方式を両立する。
- **パーサーの扱い:** パーサー拡張は、ホストから渡された文書テキストを処理して結果を返すだけとし、Vault・ネットワーク等の権限を持たない（入力として渡された文書の範囲外に触れない）。このため、パーサー呼び出しごとの権限検査を不要にする。
- **監査ログの非同期化:** 監査ログはメモリ上のキューに積み、別スレッドでまとめて書き込む。`Deny` と `Confirm` の結果は書き込み完了を待たない代わりに、終了時にキューを書き出す。
- **目標:** `check` の1回あたりの処理時間を、デスクトップの基準機で1 µs以下とする（計測はPhase 6で行う）。

## Alternatives

1. **拡張体系ごとに独自の権限を実装する。** 実装は局所的に単純だが、Contextの問題が残る。
2. **WASIのCapabilityだけで制御する。** WASM拡張には有効だが、MCP・ACP・AIプロバイダーなどWASM外の主体を扱えない。
3. **OSのサンドボックスに委ねる。** プラットフォームごとに粒度が異なり、Vault・文書単位の制御ができない。
4. **操作ごとに毎回範囲照合する。** 実装は単純だが、大量のファイル読み込み（索引作成）で負荷が大きい。ハンドル方式と世代番号で同等の安全性を保てるため採用しない。

## Consequences

- 利用者は全主体の権限を一か所で確認・取り消しできる。
- 権限の検査経路が一つになり、§24.3・§24.4の権限テストを共通化できる。
- 既定拒否・Vault単位の付与・確認省略の制限により、初回利用時の確認操作が増える。確認のまとめ表示で負担を抑える。
- リモートAIへの文書送信は常に確認が必要になり、AI Chatの操作が1手順増える。
- `app-core` の責務が増える。権限名と範囲型のバージョニングが必要になる。
- すべての保護対象をホストサービス経由にするため、ホストサービスAPIの設計がPhase 6の前提になる。

## 検証

- 範囲照合: Property-based Testingで、正規化後にVault外を指すパス（`..`、シンボリックリンク、Unicode正規化の差、大文字・小文字の差）が許可されないことを検証する。
- 失効: 取り消し後、既存ハンドルの次の操作が拒否されることを検証する。
- 既定拒否: 宣言のない権限、付与のない権限、判定エラーがすべて `Deny` になることを検証する。
- 記録: 監査ログに文書内容とシークレットが含まれないことを検証する。
- シークレット: 他の主体の名前空間のシークレットにアクセスできないこと、`secret.use` で付与時に固定した接続先以外へ認証情報が送られないこと、アンインストールで名前空間のシークレットが削除されることを検証する。
- 性能: `check` とハンドル操作のベンチマークを作り、§9の目標値と比較する。
