# ADR-0004: Markdownパーサーの選定・分離・実行方式

- **Status:** 採用（Accepted）
- **日付:** 2026-11-08
- **関連:** 統合開発計画 §6／実行計画 D-01、P0-06、P0-08／[`research/P0-08-markdown-parser.md`](../research/P0-08-markdown-parser.md)／[`requirements/parser.md`](../requirements/parser.md)／[`requirements/non-functional.md`](../requirements/non-functional.md) NFR-P03、NFR-P08／ADR-0002、ADR-0008

## Context

統合開発計画 §6.2は、ブロック構文・インライン構文の拡張フック、実行順序と優先順位、原文とソース位置の保持を求める。§6.1は、Obsidian Markdownパーサーを標準パーサーとは独立した拡張とする。NFR-P03は、1 MBのMarkdownで1文字の編集後の再解析を5 ms以内とする。

P0-08で pulldown-cmark 0.13.6、comrak 0.59.0、markdown-rs 1.0.0、markdown-it 0.6.1、tree-sitter-md 0.5.4 を比較した。

- 構文を追加する仕組みを持つのはmarkdown-itだけである。markdown-itは2024-07以降更新されておらず、病的な入力で49秒かかる場合があった。
- 拡張フックの無いパーサーでは、解析後の後処理でインライン構文を正しく追加できない（`[[x*y*z]]` の中の強調が先に解析される）。インライン構文の拡張は、標準パーサーの解析の途中で規則を呼び出す必要がある。
- 1 MBの全体解析は最速のpulldown-cmarkでも約8〜11 msで、NFR-P03を満たさない。
- pulldown-cmark・comrak・markdown-rsはCommonMark spec 0.31.2の全652例に適合した。pulldown-cmarkとcomrakは病的な入力でも100 ms以下だった。

利用者の決定（2026-11-08）: 標準パーサーを独自に実装する。すべてのパーサーをWASMにし、互いに分離する。パーサーは第三者のパーサー拡張と組み合わせて使えなければならない。

## Decision

### 1. 標準Markdownパーサーは独自に実装する

- `parser-markdown` クレートに、CommonMark spec 0.31.2に基づく標準Markdownパーサーを独自に実装する。GFMなどの拡張構文は [`requirements/parser.md`](../requirements/parser.md) §2の構文機能として実装する。
- 拡張フック（ブロック規則・インライン規則の追加、実行順序の指定、ノードの登録）の規則方式はmarkdown-itを参考にする。標準パーサー自身の拡張構文も同じ仕組みで実装する。
- 位置はUTF-8のバイト位置とする（ADR-0003と同じ）。
- 編集箇所を含むブロックだけを再解析する仕組みをパーサーの設計に含め、NFR-P03を満たす。文書全体に影響する構文（リンク参照定義、閉じていないコードブロック・HTMLブロック・ブロックコメント）の扱いはSpecで定める。

### 2. パーサーの分離

- 標準Markdown、Obsidian Markdown、各埋め込み言語（requirements/parser.md §4）のパーサーを、それぞれ独立したクレート・独立したWASMモジュールとする（`parser-markdown`、`parser-obsidian` など。ADR-0002の分割基準1）。
- パーサーのクレートは `parser-api` にだけ依存し、他のパーサーのクレートに依存しない。ホスト（`document`・`app-core`）は特定のパーサーに依存しない。
- 標準パーサーも交換可能な1つのモジュールとして扱う。パーサーが1つも無い、または使えない場合は、文書をプレーンテキストとして扱う（統合開発計画 §6.4）。

### 3. 第三者の拡張との組み合わせ（ホスト経由の実行時の合成）

- 拡張パーサー（Obsidian Markdownパーサー、第三者のパーサー拡張）は、規則をホストに登録する。登録内容は、規則の種類（ブロック・インライン）、**規則を試す開始文字（宣言）**、順序の制約（他の規則の前・後）、属する構文機能とする。
- 標準パーサーは解析中、登録された開始文字の位置に来たときだけ、ホストを経由して拡張パーサーの規則を呼び出す。規則は、認識した範囲とノードを返すか、認識しなかったことを返す。開始文字の宣言により、モジュールをまたぐ呼び出しを候補の位置に限る。
- 複数の拡張の規則の順序はホストが決定的に決め、同じ開始文字・同じ順序の制約で競合する場合は検出して利用者に示す（§6.2の構文競合）。
- 拡張パーサーが使えない、失敗した、または時間・メモリの上限（NFR-P08）を超えた場合、その規則は認識しなかったものとして解析を続ける。原文は変更しない（§6.4）。
- 埋め込み言語のパーサーは、Markdownパーサーが出力した埋め込み領域（言語ID・範囲）をホストから受け取って解析する。標準パーサーの解析の途中には呼び出さない。
- パーサー拡張には保護対象へのアクセス手段を与えない（ADR-0008）。
- 呼び出しの回数・データの受け渡しを減らす方式（候補位置をまとめて渡すなど）と、`parser-api` の詳細はSpecで定める。

### 4. 実行方式と移行時期

- すべてのパーサーをWASMモジュールとして実行する。
- WASMランタイムの整備はPhase 6のままとする（D-01）。Phase 2〜5では各パーサーをネイティブで実装するが、§2・§3と同じくホスト経由で合成し、パーサーどうしを直接呼び出さない。Phase 6でWASMへ移しても、合成の方式とパーサーの組み合わせは変わらない。
- パーサーはファイル・スレッド・時刻などOSの機能に直接依存しない。
- WASMでの実行（モジュールをまたぐ呼び出しを含む）がNFR-P03を満たすかをP0-06で計測する。満たさない場合は、§3の呼び出し方式の見直しを含めて本ADRを改訂する。

### 5. CJKの句読点に隣接する強調

- 既定はCommonMarkの規則に従う（`**この文は重要です。**但` は強調にならない）。Obsidianの編集画面（Live Preview・ソースモード）でも、閉じの記号は閉じとして認識されなかった（検証記録 §6.1）。
- CJKの句読点に隣接する強調を認める規則を、標準パーサーの構文機能 `cjk-friendly-emphasis`（既定オフ）として提供する。規則はcomrakの `cjk_friendly_emphasis` を参考にSpecで定める。

### 6. 検証

- CommonMark spec testsの全例への適合をCIで確認する。spec testsのデータの取得方法とライセンスの扱いは、テストの実装時に決める（2026-11-14 追記: 利用者の決定によりデータ（CC BY-SA 4.0）をリポジトリに含める。[Spec: parser-markdown](../spec/parser-markdown.md) §2）。
- pulldown-cmarkとcomrakを開発時の依存（`dev-dependencies`）に限って使い、任意の入力で出力を比較する差分試験を行う。製品のバイナリには含めない（2026-11-14 追記: 参照実装どうしで結果が分かれる入力があるため、markdown-rs を加えた3つのいずれかとの一致を条件とした。同 §8）。
- P0-08の病的な入力（[検証記録](../research/P0-08-markdown-parser.md) §3.6）を、時間の上限付きの試験に含める。Fuzz Testingを行う（実行計画 §8）。
- 複数の拡張（Obsidian Markdownパーサーと試験用の第三者拡張）を同時に有効にした組み合わせの試験を行う。

## Alternatives

1. **comrakを使い、不足する構文をフォークで補う。** 適合率・Obsidian構文の対応範囲・保守・病的な入力への耐性はそろう。Obsidian構文が標準パーサーに組み込まれた構成になり、パーサーの分離に合わない。
2. **pulldown-cmarkをフォークして拡張フックを追加する。** 最も速い。内部構造への大きな変更になり、上流との差分を保守し続ける必要がある。
3. **markdown-itを使う。** 拡張フックを持つが、保守が止まっており、病的な入力に弱い。
4. **標準パーサーの中核をライブラリとして共有し、拡張ごとにそれを取り込んだモジュールを作る。** モジュールをまたぐ呼び出しが無く速い。第三者の拡張とObsidian拡張を同時に組み合わせられないため採らない。
5. **規則をデータ（宣言）だけで登録し、ホストが解釈する。** モジュールをまたぐ呼び出しが無い。表現できる構文が限られる。§3では開始文字の宣言にだけこの考え方を使う。

## Consequences

- §6.2の拡張フック、パーサーの分離、第三者の拡張との組み合わせを、パーサーの設計で直接満たせる。
- インライン構文の拡張ごとに、開始文字の位置でモジュールをまたぐ呼び出しが起きる。NFR-P03への影響はP0-06で計測するまで分からない。
- Phase 2の作業量が増える。標準Markdownの解析はM3（Reading View）までに必要である。
- CommonMarkとの差異は、spec testsと差分試験で検出する。
- Reading ViewでのCJKの句読点に隣接する強調の扱いは未確認である（§5の既定値の根拠は編集画面での確認）。
