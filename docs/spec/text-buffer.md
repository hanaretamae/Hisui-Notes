# Spec: テキストバッファ（`text-buffer`）

- **状態:** 草案（2026-11-14）。M2（実行計画 §4）の範囲。§9 の1〜4は利用者が決定済み。
- **関連:** 統合開発計画 §5.2、§18.4／ADR-0002／ADR-0003／[P0-09](../research/P0-09-text-buffer.md)／[NFR](../requirements/non-functional.md) NFR-P01、NFR-P02

## 1. 目的と範囲

1つの文書の原文を保持し、編集・編集履歴・位置変換・書記素境界・スナップショットを提供する。文書形式・ファイル・UI・時刻に依存しない。

範囲外（他のクレート・Specで定める）:

| 事項 | 担当 |
|---|---|
| カーソル・選択範囲・複数カーソル、編集コマンド（Backspaceの単位など） | `document`（文書セッション）とエディターのSpec |
| 入力のまとまりによるUndoの区切りの判定（時間・入力の種類） | 同上。`text-buffer` は区切りを指示されるだけ（§6.3） |
| 変更の購読・配送 | `document`。`text-buffer` は適用結果を戻り値で返す（§5.4） |
| ファイルの読み書き、文字コード、BOM | `vault` |
| クラッシュリカバリーの記録の保存 | `document`・`vault`。`text-buffer` はトランザクションを直列化できる形で提供する |
| 表示上の行（折り返し）、右から左のテキストの表示位置 | `ui-gpui` |

## 2. 原文の保持

- 内容は常に正しいUTF-8の文字列である。
- 受け取った文字列を正規化・変換しない（Unicode正規化、改行コードの変換、BOMの除去をしない。統合開発計画 §18.4）。
- 内容は、編集の結果としてのみ変わる。

## 3. 位置

### 3.1 基本単位

- 公開APIの位置は、内容の先頭からのUTF-8のバイト位置（`usize`）とする（ADR-0003 §1）。範囲は半開区間 `start..end`。
- ropeyの型と文字（コードポイント）位置は公開APIに出さない。

位置の検査（すべての操作で共通）:

| 条件 | エラー |
|---|---|
| 位置が内容の長さを超える | `OutOfBounds { offset, len }` |
| 位置が文字境界でない（UTF-8の途中） | `NotCharBoundary { offset }` |
| 範囲の `start > end` | `InvalidRange { start, end }` |

パニックしない。

### 3.2 行

- 行区切りは LF（U+000A）、CR（U+000D）、CRLF（CR + LF の2文字で1つ）とする。CommonMarkの行末の定義と同じ。VT・FF・NEL・LS・PSは行区切りとしない（§9-1）。
- 行の数は「行区切りの数 + 1」。空の内容は1行。末尾が行区切りで終わる場合、最後の行は空の行になる。
- 行番号は0始まり。行の範囲は行区切りを含まない（行区切りの範囲は別に取得できる）。
- CRLFのCRとLFの間のバイト位置は文字境界であり、位置としては有効。その位置は行の終わりとみなさず、CRLF全体の前の位置と同じ行に属する（§9-1）。

### 3.3 位置変換

次の変換を提供する。いずれも §3.1 の検査を行い、O(log n) で動作する。

| 変換 | 用途 |
|---|---|
| バイト位置 ⇔ コードポイント位置 | 汎用 |
| バイト位置 ⇔ UTF-16位置（先頭から） | IME、プラットフォームのテキスト入力API |
| バイト位置 ⇔（行, 行内のバイト位置） | 描画、パーサーの位置表示 |
| バイト位置 ⇔（行, 行内のUTF-16位置） | LSP（既定の位置の単位がUTF-16） |
| 行 → 行の範囲・行区切りを含む範囲 | 描画 |

- 行内の位置の有効な範囲は、行区切りを持つ行では `0` 以上「行区切りを含む行の長さ」未満、最後の行（行区切りを持たない）では `0` 以上「行の長さ」以下とする。CRLFの間の位置（§3.2）はCRの後ろの位置として表せる。
- 変換先の値が範囲外の場合（行番号が行数以上、行内の位置が有効な範囲の外、UTF-16位置がサロゲートペアの途中など）はエラーを返す。丸めた位置を返す操作は、エディターのSpecで必要になった時点で追加する。
- 往復の一致: 有効な位置 `p` について、`p` を任意の単位へ変換して戻すと `p` に一致する。

### 3.4 書記素クラスタ

- 書記素クラスタは `unicode-segmentation` の拡張書記素クラスタ（UAX #29）とする（ADR-0003 §2）。CRLFは1つの書記素クラスタになる。
- 提供する操作:
  - `is_grapheme_boundary(offset)`
  - `next_grapheme_boundary(offset)`・`prev_grapheme_boundary(offset)`（内容の末尾・先頭では `None`）
  - `next_char_boundary(offset)`・`prev_char_boundary(offset)`（コードポイント単位。結合文字をコードポイント単位で扱う操作のため）
- 結果はRopeの内部のチャンク境界に依存せず、同じ内容の文字列全体に `unicode-segmentation` を適用した結果と一致する。

## 4. 読み出し

- 長さ（バイト、コードポイント、UTF-16、行数）
- 範囲の文字列（`String` への複製）、範囲のチャンクの列（`&str` の列。複製しない）
- 全体の文字列

読み出しは内容・版を変えない。

## 5. 編集

### 5.1 範囲置換

1回の編集を範囲置換 `Edit { range, insert }` で表す。`range` のバイト範囲を削除し、`range.start` に `insert` を挿入する（ADR-0003 §3）。

- `range` は §3.1 の検査を受ける。
- `range` が空で `insert` も空の編集は「変化なし」とする。

### 5.2 トランザクション

- 編集の列を1つのトランザクションとして適用する。列の中の各編集の範囲は、それより前の編集を適用した後の内容に対する位置として解釈する（ADR-0003 §3）。
- 原子性: 列の中のいずれかの編集が検査に失敗した場合、エラーを返し、内容・版・履歴を変えない。
- すべての編集が「変化なし」の場合（空の列を含む）は適用しない。版・履歴を変えず、適用結果として `None` を返す。

### 5.3 版番号

- 版番号は `u64` で、バッファの作成時に0。
- 内容を変えたトランザクション（Undo・Redo・履歴の移動を含む）の適用ごとに1増える。それ以外では変わらない。
- 同じバッファの版番号は単調増加し、同じ版番号は同じ内容に対応する。

### 5.4 適用結果

内容を変えた操作（編集、Undo、Redo、履歴の移動）は、適用結果 `Change` を返す。

- `version`: 適用後の版番号
- `edits`: 実際に適用した範囲置換の列。各要素は、適用前の範囲・削除された文字列・挿入された文字列を持つ（「変化なし」の編集は含めない）

`Change` は `serde` で直列化・復元できる（クラッシュリカバリーの記録、変更通知に使う）。

適用結果の性質:

- 適用前の内容に `edits` を順に適用すると、適用後の内容になる。
- `edits` の逆（各要素の削除と挿入を入れ替え、順序を逆にしたもの）を適用後の内容に適用すると、適用前の内容に戻る。

### 5.5 位置の補正

古い版に対する位置（解析結果、カーソル）を新しい版へ補正する関数を提供する（ADR-0003 §5）。

- `map_offset(offset, bias, &change) -> usize`。`change` の各範囲置換（適用前の範囲 `start..end`、挿入した文字列の長さ `n`）を順に適用して補正する。
  - `offset < start`: 変わらない。
  - `offset > end`、または `start < end` かつ `offset == end`（削除された範囲の直後）: 置換の後ろへ移る（`offset - (end - start) + n`）。
  - それ以外（`offset == start`、または削除された範囲の内側）: `bias` が `Before` なら `start`、`After` なら `start + n`。
- 文字境界の位置を補正した結果は、新しい版の内容の文字境界である。

## 6. 編集履歴（Undo/Redo）

### 6.1 構造（Undo tree）

- 履歴は木とする（2026-11-14 利用者の決定）。Undoの後に新しい編集をしても、それまでの分岐を破棄しない。
- 木の各節点（以下「項目」）は1つ以上のトランザクションのまとまりで、Undoの単位になる。根は、バッファ作成時の内容に対応する空の項目。
- 各項目は、作成順に振られる識別子 `HistoryId`（根は0、以後1ずつ増える）、親、子の列（作成順）を持つ。
- バッファは「現在の項目」を1つ持つ。現在の内容は、根から現在の項目までの経路上のトランザクションをすべて適用した内容に等しい（不変条件）。
- 各項目は、子のうち最後に通った（作成した、またはRedo・移動で入った）子を記録する。

### 6.2 編集の追加

編集の適用時に、呼び出し側が履歴の扱いを指定する。`text-buffer` は時刻を参照しない（同じ入力に対して結果を決定的にするため）。

| 指定 | 動作 |
|---|---|
| `NewGroup` | 現在の項目の子として新しい項目を作り、現在の項目にする。既存の子（分岐）はそのまま残る |
| `MergeWithPrevious` | 現在の項目に追加する。ただし、現在の項目が根の場合、子を持つ場合、または直前の履歴の操作がUndo・Redo・移動だった場合は `NewGroup` と同じ |

- 内容を変えたトランザクションはすべて履歴に入る。外部での変更の再読み込みも、呼び出し側が `NewGroup` の1つの項目として適用する（2026-11-14 利用者の決定。差分の計算方法は `vault`・`document` のSpecで定める）。

### 6.3 Undo・Redo・移動

- `undo()`: 現在の項目のトランザクションを逆順に取り消し、親を現在の項目にする。親の「最後に通った子」は取り消した項目になる（直後の `redo()` で戻れる）。現在の項目が根の場合は `None`。
- `redo()`: 現在の項目の「最後に通った子」のトランザクションを適用し、その子を現在の項目にする。子が無い場合は `None`。
- `redo_to(child)`: 指定した子へ進む。`child` が現在の項目の子でない場合はエラー（`NotAChild`）。
- `goto(id)`: 任意の項目へ移動する。現在の項目から共通の祖先までUndoし、そこから `id` までRedoする。`id` が存在しない場合はエラー（`UnknownHistoryId`）。現在の項目と同じ場合は `None`。経路上の各段階で、親の「最後に通った子」をその段階で通った子にする（上る段階は `undo()` と同じ。共通の祖先では下る先の子になる）。
- いずれも、内容を変えた場合は全体を1つのトランザクションとして適用し、版番号を1増やし、`Change` を返す。受け手は通常の編集と区別せずに処理できる。

### 6.4 履歴の参照

- 現在の項目の `HistoryId`。
- 各項目の親、子の列、最後に通った子、含むトランザクションの数。UIでの分岐の表示と、作成順の移動（`HistoryId` の前後）に使う。

### 6.5 上限

- M2では履歴の項目数・メモリに上限を設けない。編集履歴を含むメモリ使用量を計測した後に決める（P0-09 §6、§9-5）。

## 7. スナップショット

- `snapshot()` は、その時点の内容と版番号を持つ不変のスナップショットを返す（ADR-0003 §5）。O(1)（Ropeの複製）。
- スナップショットは §3・§4 の読み出しをすべて提供し、`Send + Sync` で、別スレッドの解析・索引・保存に渡せる。
- その後の編集はスナップショットの内容を変えない。

## 8. 不変条件と検証

不変条件:

- 内容は正しいUTF-8である（§2）。
- 版番号は内容を変えた操作でのみ1ずつ増える（§5.3）。
- 失敗した操作は内容・版・履歴を変えない（§5.2）。

テスト（ADR-0003「検証」、実行計画 §8）:

- Property-based Testing（`proptest`）:
  - 任意の文字列と任意のトランザクション列について、内容が `String` に同じ編集をした結果と一致する。
  - 任意の編集の後、Undoをすべて行うと最初の内容に戻り、Redoをすべて行うと最後の内容に戻る。
  - 任意の編集・Undo・Redo・`goto` の列の後、現在の内容が、根から現在の項目までの経路上のトランザクションを適用した内容に等しい（§6.1 の不変条件）。各項目へ `goto` したときの内容は、その項目を最後に離れたときの内容に等しい。
  - `Change` の性質（§5.4）が成り立つ。
  - 任意の有効な位置で、§3.3 の変換が往復で一致し、標準ライブラリで同じ内容を数えた結果と一致する。
  - 書記素境界の結果が、文字列全体での `unicode-segmentation` の結果と一致する。
  - `map_offset` の結果が新しい版の文字境界である。
- 書記素のチャンク境界: テストではropeyの `small_chunks` を有効にし、国旗（地域指示子）、ZWJ連結の絵文字、結合文字（`e` + U+0301）、インド系文字体系の結合子音、CRLFがチャンク境界をまたぐ内容で検証する。
- 異常系: 範囲外・文字境界でない位置・逆転した範囲でエラーを返し、パニックしない。原子性（§5.2）。

性能（NFR-P01、NFR-P02）: 10 MB・20万行の内容で、1回の編集・位置変換・書記素境界の計算が O(log n) で、P0-09と同等の値であることをベンチマークで確認する。

## 9. 決定事項と未決の事項

利用者の決定（2026-11-14）:

1. **行区切り:** LF・CR・CRLFのみ（§3.2）。VT・FF・NEL（U+0085）・LS（U+2028）・PS（U+2029）は通常の文字として扱う。ropeyは `default-features = false` と `cr_lines`（と `simd`）で使う。
2. **Backspaceの単位（ADR-0003 §2の残り）:** エディターのSpecで決める。`text-buffer` は書記素単位・コードポイント単位の両方の境界を提供する（§3.4）。→ [文書セッションのSpec](document-session.md) §5.3.1 でコードポイント単位と決定（2026-11-14）。
3. **履歴の形:** 分岐する履歴（Undo tree、§6）。
4. **外部での変更の再読み込み:** Undo可能な1つの項目として履歴に入れる（§6.2）。

未決:

5. **履歴の上限:** M2では上限を設けず、編集履歴を含むメモリ使用量を計測した後に決める（§6.5）。Undo treeは分岐を破棄しないため、線形の履歴より増えやすい。
