# P0-09: テキストバッファ（Rope）の選定

- **調査日:** 2026-11-08
- **目的:** `text-buffer` クレート（ADR-0002）の基盤とするRope実装を選び、性能要件（[`requirements/non-functional.md`](../requirements/non-functional.md) NFR-P01、NFR-P02）を満たすか確認する。
- **計測プログラム:** [`spikes/p0-09-rope-bench/`](../../spikes/p0-09-rope-bench/)（再現手順は同ディレクトリのREADME）

## 1. 候補

| crate | 版 | 最終公開 | ライセンス | 判断 |
|---|---|---|---|---|
| `ropey` | 1.6.1（2.0.0-beta.1あり） | 2025-08 | MIT OR Apache-2.0 | 計測対象。Helixエディターが使用。直近の取得数が多い |
| `crop` | 0.4.3 | 2025-04 | MIT | 計測対象。バイト位置が基本のAPI |
| Zed `rope` | — | — | **GPL-3.0-or-later** | 除外（ADR-0011の許可リスト外） |
| `jumprope` | 1.1.2 | 2023-05 | ISC OR Apache-2.0 | 除外（複製の軽い永続データ構造ではない。更新が少ない） |
| `xi-rope` | 0.3.0 | 2019-06 | Apache-2.0 | 除外（保守されていない） |

Zedの `sum_tree`（Apache-2.0）はRopeではなく汎用の木構造のため、今回は対象外とした。

## 2. 方法

- **環境:** NixOS、12コア、メモリ15 GB、rustc 1.99.0、`--release`。
- **文書:** 決定的な乱数で生成した10,485,780バイト、205,259行、4,873,802文字、4,430,146書記素クラスタの文書。英語、日本語、韓国語、中国語、タイ語、ヒンディー語（結合子音）、アラビア語、ヘブライ語、絵文字（ZWJ連結 `👩‍💻`、国旗 `🇯🇵`）、結合文字（`e` + U+0301）を混在させた。
- **正確性の確認:** 200 KBの文書に2,000回の編集（行頭への挿入・行の削除）を行い、`String` に同じ編集をした結果と内容が一致すること、書記素クラスタ数とUTF-16長が `unicode-segmentation` と標準ライブラリの結果と一致すること、全行頭のUTF-16位置が一致することを確認した。
- **計測:** 各3回実行した。

## 3. 結果

### 3.1 正確性

| 項目 | ropey | crop |
|---|---|---|
| 編集後の内容 | 一致 | 一致 |
| UTF-16長・行頭のUTF-16位置 | 一致 | 一致 |
| 書記素クラスタ | 一致（ropeyは書記素の機能を持たないため、`unicode-segmentation` の `GraphemeCursor` をチャンク単位で使う補助関数で計数） | **不一致**（65,909 対 正解65,907） |

**cropの不具合:** cropの `graphemes()` は、国旗の絵文字（地域指示子2文字、例: `🇯🇵` = U+1F1EF U+1F1F5）がRope内部のチャンク境界をまたぐと、2つの書記素に分割する。752バイトの文書で再現した（`spikes/p0-09-rope-bench/src/bin/diag.rs`）。同じ版の `unicode-segmentation` を使う自前の補助関数では正しく数えられたため、cropのチャンク境界での前方文脈の扱いの問題と考えられる。

### 3.2 性能（3回の範囲）

| 項目 | ropey 1.6.1 | crop 0.4.3 |
|---|---|---|
| 10 MBの文字列から構築 | 7.6〜12.7 ms | 7.9〜8.1 ms |
| 構築後のメモリ増加 | 11,192 KiB | 10,304 KiB |
| 1万回の編集（行頭への挿入・行の削除） | 10.4〜15.5 ms | 15.2〜16.6 ms |
| 1回の挿入の最悪値（1,000回中） | 4.8〜14.9 µs | 6.3〜11.8 µs |
| 行→バイト・バイト→行 各10万回 | 36〜52 ms | 64〜66 ms |
| バイト→UTF-16・UTF-16→バイト 各10万回 | 76〜111 ms | 90〜94 ms |
| 1万行の書記素の走査 | 19.5〜31.1 ms | 19.9〜20.0 ms |
| 複製1,000回と各複製への編集 | 3.7〜7.0 ms | 3.2〜3.8 ms |
| 複製1,000個を保持した後のメモリ増加 | 14,472 KiB | 17,672 KiB |

### 3.3 要件との比較

- 1回の編集の最悪値は15 µs以下で、NFR-P02（入力から描画まで中央値16 ms）の予算の0.1%未満。
- 位置変換は1回あたり1 µs前後で、描画や解析で多数回呼んでも予算内に収まる。
- 複製は1回あたり数 µsで、編集を続けながら解析・保存用の不変スナップショットを渡せる。
- **両者とも性能要件を満たし、性能は選定の決め手にならない。**

## 4. API上の違い

| 項目 | ropey 1.6.1 | crop 0.4.3 |
|---|---|---|
| 位置の基本単位 | 文字（コードポイント）。バイト・UTF-16・行との変換関数あり | バイト。UTF-16・行との変換関数あり |
| 文字境界でないバイト位置 | 行の検索などでは受け付ける | パニックする（誤った位置の検出には有利） |
| 書記素 | 機能なし（`unicode-segmentation` を組み合わせる） | 機能あり（3.1の不具合あり） |
| 次の版 | 2.0（バイト位置が基本）がベータ | — |

## 5. 結論

- `ropey` 1.6.1を採用する。理由: 正確性の確認で不具合がなかった、利用実績が多い、性能要件を満たす。
- `text-buffer` の公開APIはバイト位置（UTF-8）を基本とし、ropeyの文字位置は内部に閉じ込める。ropey 2.0（バイト位置が基本）への移行、または他の実装への交換を `text-buffer` の内部だけで行えるようにする。
- 書記素クラスタの処理は `unicode-segmentation` の `GraphemeCursor` をチャンク単位で使う自前の実装とし、国旗・ZWJ連結・結合文字・インド系文字体系の結合子音をチャンク境界に置いたテストを用意する。
- cropの不具合は上流に報告していない（外部への報告は利用者の判断で行う）。
