# P0-06: WASMランタイムの比較

- **調査日:** 2026-11-08
- **状態:** 完了。Aを採用した（[ADR-0005](../adr/0005-wasm-runtime.md)、2026-11-08）。
- **目的:** すべてのパーサーをWASMで実行する方針（[ADR-0004](../adr/0004-markdown-parser.md)）と、ユーザープラグイン（統合開発計画 §19）の実行基盤として、WasmiとWasmtime（Pulley）を比較する。NFR-P03（再解析5 ms以内）、NFR-P04（起動時間）、NFR-P08（時間・メモリ上限）との適合と、ADR-0004 §3のホスト経由の規則呼び出しの費用を確認する。
- **計測プログラム:** [`spikes/p0-06-wasm-runtimes/`](../../spikes/p0-06-wasm-runtimes/)（再現手順は同ディレクトリのREADME）

## 1. 候補

| ランタイム | 版 | 実行方式 | ライセンス | 依存crate数※ |
|---|---|---|---|---|
| Wasmi | 2.0.0（2026-09） | インタープリター（Wasmi独自のバイトコードへ翻訳） | MIT/Apache-2.0 | 18 |
| Wasmtime + Pulley | 50.0.1（2026-11） | インタープリター（Pulleyバイトコード。事前コンパイル可） | Apache-2.0 WITH LLVM-exception | 46（実行のみ）／76（コンパイラー込み） |
| Wasmtime + Cranelift | 50.0.1 | JITコンパイル（参考。iOSでは使えない） | 同上 | 76 |

※ 計測用ホストの通常の依存（`cargo tree -e normal`）。pulldown-cmarkを含む。

- Wasmtime・Craneliftの27crateは `Apache-2.0 WITH LLVM-exception` のみで公開されている。ADR-0011の許可リストはこの表記を明示していない（例外条項は許諾を追加するもの）。
- Wasmi 2.0.0のREADMEとcrateにComponent Modelの記載は無い。Wasmtimeは `component-model` 機能を持つ（P0-07で評価する）。

## 2. 方法

- **環境:** NixOS、Intel Core i5-1335U（Pコア2・Eコア8の混在、ノートPC、`powersave`）、メモリ15 GB、rustc 1.99.0、`--release`。他の利用者アプリ（エディター・ブラウザー）が動作中。**`taskset -c 2` で1つのPコアに固定**して計測した。固定しない場合、PコアとEコアの割り当てで値が約2倍の間で揺れた。
- **ゲスト:** pulldown-cmark 0.13.6を `wasm32-unknown-unknown` 向けにビルドした276 KBのモジュール（WASIなし、`opt-level=3`、LTO）。独自のMarkdownパーサー（ADR-0004）はまだ無いため、解析の負荷の代わりとして使った。文書をホストが線形メモリに書き込み、ポインターと長さを渡す。
- **文書:** P0-08と同じ1,048,917バイトの文書と、その中央の4,109バイトの範囲（見出しから見出しまで。ブロック単位の再解析の単位の想定）。
- **ホスト経由の規則呼び出し（ADR-0004 §3）:** 同じモジュールを2つインスタンス化し、片方（パーサー）が `[` の位置（17,829箇所）ごとにホストの関数を呼び、ホストがもう片方（拡張）の規則関数を呼ぶ。ホストを呼ばない同じ走査を基準にして、1回あたりの増分を求めた。
- **上限:** 燃料（命令数）、エポック（壁時計による中断。Wasmtimeのみ）、メモリ上限（64 MiB）を、終わらないループとメモリを増やし続ける関数で確認した。
- **正確性:** 各ランタイムでの解析結果のイベント数がネイティブ（149,366）と一致することを確認した。

## 3. 結果

### 3.1 実行速度（Pコアに固定、各10回の中央値、3回の範囲）

| 構成 | 1 MBの全体解析 | ネイティブ比 | 4 KBのブロック解析 | ネイティブ比 |
|---|---|---|---|---|
| ネイティブ | 14.1〜15.2 ms | 1 | 42〜44 µs | 1 |
| Wasmtime + Cranelift | 22.2〜23.0 ms | 約1.6倍 | 72〜81 µs | 約1.8倍 |
| Wasmi（事前翻訳・遅延翻訳） | 197〜207 ms | 約14倍 | 842〜866 µs | 約20倍 |
| Wasmtime + Pulley（実行時コンパイル・事前コンパイル） | 544〜588 ms | 約39倍 | 2.25〜2.30 ms | 約54倍 |

- 同じPコアでも、時間をおいた別の計測では全構成が約2倍速かった（ネイティブ7.3 ms、Pulley 287 ms）。CPUの周波数の状態によると考えられる。**同じ実行の中でのネイティブ比は安定していた**（Pulleyは2回とも約39倍）。絶対値より比を判断に使う。
- Pulleyは、Wasmiより約2.7倍遅かった。

### 3.2 ホスト経由の呼び出し（1回あたりの増分、3回の範囲）

| 構成 | ホストの関数の呼び出し | ホストから別のインスタンスの関数の呼び出しまで |
|---|---|---|
| Wasmtime + Cranelift | 37〜108 ns | 139〜159 ns |
| Wasmi | 92〜158 ns | 321〜365 ns |
| Wasmtime + Pulley | 267〜344 ns | 927〜1,006 ns |

4 KBのブロックには `[` が約70箇所ある。規則を呼ぶ拡張が1つの場合、Pulleyでも約70 µsで、ブロックの解析時間に比べて小さい。

### 3.3 起動とメモリ（Pコアに固定、2回）

| 構成 | モジュールの準備 | インスタンス化 | 最初の小さな解析 | 常駐メモリの増加 |
|---|---|---|---|---|
| Wasmi 事前翻訳 | 翻訳 8.8 ms | 0.69〜0.74 ms | 0.06 ms | 約3.6 MiB |
| Wasmi 遅延翻訳 | 検証 2.3 ms | 0.59〜0.61 ms | 3.5 ms（使う関数をここで翻訳） | 約1.4 MiB |
| Wasmtime + Cranelift | コンパイル 364〜366 ms | 0.10 ms | 0.02〜0.03 ms | 約19 MiB |
| Wasmtime + Pulley（実行時コンパイル） | コンパイル 362〜375 ms | 0.12〜0.13 ms | 0.10〜0.11 ms | 約5 MiB |
| Wasmtime + Pulley（事前コンパイル済みの読み込み） | 0.42〜0.44 ms | 0.07 ms | 0.10 ms | 約0.6 MiB |

- Wasmtimeは、モジュールごとに数百msのコンパイルが必要になる。起動のたびに行わないためには、コンパイル結果をディスクに保存する必要がある。保存したコンパイル結果の読み込み（`Module::deserialize`）は `unsafe` で、内容を信頼できることが前提になる（改ざんされたファイルを読み込むと安全性が保証されない）。
- Wasmiはコンパイル結果の保存が不要で、起動のたびに数msで準備できる。

### 3.4 時間・メモリの上限（NFR-P08）

| 機構 | Wasmi | Wasmtime + Cranelift | Wasmtime + Pulley |
|---|---|---|---|
| 燃料（命令数）で停止 | ○（「all fuel consumed」） | ○（`Trap::OutOfFuel`） | ○（同左） |
| 燃料を有効にした場合の解析時間の増加 | 約+3% | 約+23% | 約+23% |
| 壁時計による中断（エポック） | 機構なし | ○（50 ms後に `Trap::Interrupt`、51.8 ms で停止） | ○（51.3 ms で停止） |
| エポックを有効にした場合の解析時間の増加 | — | 約+21% | 約+15% |
| メモリ上限（64 MiB） | ○（1,024ページで増加が失敗） | ○ | ○ |
| 停止後の同じインスタンスの再利用 | 可 | 可 | 可 |

- 燃料の単位はランタイムごとに異なる（1 MBの解析でWasmi 40.8億、Wasmtime 1.66億）。上限値はランタイムごとに較正する必要がある。
- Wasmiで壁時計の上限を設けるには、燃料を時間に換算して設定する（計測機での換算: 10億の燃料で約0.58秒）。

### 3.5 ホストのバイナリサイズ（strip後）

| 構成 | サイズ | ランタイムなしからの増加 |
|---|---|---|
| ランタイムなし（基準） | 0.84 MB | — |
| Wasmi | 3.32 MB | +2.5 MB |
| Wasmtime（実行のみ。事前コンパイル済みのPulleyを実行） | 1.77 MB | +0.9 MB |
| Wasmtime（Cranelift・Pulleyのコンパイラー込み） | 12.44 MB | +11.6 MB |

Wasmtimeを実行のみの構成にした場合、モジュールのコンパイルは別の場所（ビルド時、または配布前）で行う必要がある。

## 5. 結論と選択肢（2026-11-08にAを採用。ADR-0005）

- **A. Wasmiを全プラットフォームで使う（採用）。**
  - 全プラットフォームで同じ実装・同じ挙動になり、iOSでも使える。
  - JITとコンパイル結果の保存が無く、攻撃面が小さい。プライバシー・セキュリティ優先の方針（requirements/non-functional.md）に合う。
  - 起動が速く、コンパイル結果の保存が要らない。燃料による停止の負荷が小さい（約+3%）。
  - 4 KBのブロック解析は約0.9 msで、ブロック単位の再解析（ADR-0004）と組み合わせればNFR-P03を満たす見込み。1 MBの文書を開いたときの全体解析は約0.2秒かかる。
  - Component Modelの記載が無い。P0-07でComponent Model（WIT）を選ぶ場合はAを採れない。
  - 壁時計による中断が無く、燃料で近似する。
  - 将来、デスクトップで性能が不足した場合に備え、ホスト側のランタイムの層を差し替え可能にしておく。
- **B. Wasmtimeを使い、デスクトップ・AndroidはCranelift、iOSはPulleyにする。** 最も速い（デスクトップでネイティブの約1.6倍）。Component Modelを使える。JITの攻撃面、コンパイル結果の保存と検証、バイナリサイズ（+11.6 MB）、プラットフォームによる実行方式の違いを負う。AndroidでのCraneliftの動作は未確認。
- **C. Wasmtime + Pulleyだけを使う（事前コンパイル済みのモジュールを配布）。** バイナリは最小だが、今回の計測で最も遅く（ネイティブの約39〜54倍）、NFR-P03の余裕が小さい。第三者の拡張も事前コンパイルが必要になる。

P0-07（プラグインABI: Component Model / WIT、またはコアモジュール + 独自ABI）と結論が連動する。Aを採る場合、ABIはコアモジュール + 独自ABIになる。
