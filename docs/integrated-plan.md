# Hisui Notes — 統合開発計画

> **位置づけ:** プロジェクト全体の目的・構成・機能範囲・開発工程を定める上位計画。Requirements、Spec、ADRへ分割した項目は、該当節を分割先への参照に置き換え、内容を二重管理しない。実行計画と要決定事項は [`development-plan.md`](development-plan.md) で管理する。

## 1. プロジェクト概要

### 1.1 目的

RustとGPUIを基盤とする、マルチプラットフォーム対応のモジュール式文書編集・ノートアプリケーションを開発する。

特定の文書形式、プログラミング言語、自然言語に依存しない設計とし、文書編集、表示、解析、AI連携、拡張機能を独立したモジュールとして構成する。

Markdownを標準搭載する文書形式の一つとし、標準MarkdownおよびObsidian Markdownへの対応を提供する。

### 1.2 対象プラットフォーム

- Linux
- Windows（保留）
- macOS（保留）
- Android
- iOS（保留）

Windows・macOS・iOSは、指示があるまで開発・検証を保留する。保留中は、これらのプラットフォームを各Phaseの完了条件から除外し、Linux（とAndroid）で先へ進める。保留中も、Core・Platform・Frontendの分離と、OS固有の型を共通APIに持ち込まない設計（§3）は維持し、再開時に移植できる状態を保つ。

### 1.3 基本方針

- Rustによるアプリケーションロジックの共通化。
- 全プラットフォームでGPUIをUIフレームワークとして使用する。
- UI、アプリケーションコア、OS固有機能を分離する。
- モジュール式UI（Modular UI）を採用する。
- 言語・文書形式に依存しない共通編集基盤を提供する。
- 自然言語の多言語対応を基本設計に含める。
- Unicodeを基本文字表現として採用する。
- WASMによるパーサー・ユーザープラグインの拡張。
- LSP、MCP、ACPなどの標準プロトコルに対応する。
- コア機能と拡張機能の責務を明確に分離する。
- ローカルファーストのデータ管理。
- APIのバージョニングと後方互換性を考慮する。
- 機能の追加・交換・無効化を容易にする。
- セキュリティ、保守性、性能を重視する。

## 3. API・境界設計

### 3.1 基本原則

- UIとアプリケーションコアを独立させる。
- Core、Platform、Frontendの間に明確な境界を設ける。
- モジュール間の依存関係を明示する。
- 循環依存を禁止する。
- 内部実装への直接アクセスを避け、公開APIを通じて連携する。
- UIフレームワーク固有の型を共通APIに持ち込まない。
- 文書形式や言語固有の型をアプリケーションコアの共通インターフェースに持ち込まない。

### 3.2 アプリケーションAPI

- UIとコアの間に共通APIを設ける。
- Command、Query、Eventを分離する。
- 非同期処理とイベント通知に対応する。
- APIをバージョニングし、後方互換性を考慮する。
- エラー形式とデータ交換形式を統一する。
- APIの仕様、権限、ライフサイクルを明文化する。
- 長時間処理やキャンセル可能な処理を管理できるようにする。

### 3.3 拡張API

各拡張は共通の拡張管理機構を利用する。

- 拡張ID・バージョン・依存関係を管理する。
- 必要なCapabilityを宣言する。
- 有効・無効化を個別に管理する。
- Lazy Loadingに対応する。
- 拡張間の通信は公開API・イベントを介する。
- 拡張固有のAPIは共通APIと分離する。
- APIの互換性を検証する。
- 拡張の追加・削除によって既存データを破壊しない。

### 3.4 データ交換

- モジュール間のデータ型を明確に定義する。
- プラットフォーム固有の型を共通データ型に直接混入させない。
- シリアライズ形式とバージョニングを管理する。
- 大きな文書やバイナリデータは不要な複製を避ける。
- エラー・警告・診断情報を共通形式で扱う。

## 4. 言語・文書形式に依存しない設計

### 4.1 基本原則

アプリケーションコアはMarkdownなどの特定の文書形式や、Rust・Pythonなどの特定のプログラミング言語に依存させない。

文書の読み書き、テキスト編集、表示、解析、言語機能を独立したレイヤーとして管理する。

プログラミング言語と自然言語も別の概念として扱う。

### 4.2 共通文書モデル

- 文書の種類に依存しない共通Document Modelを定義する。
- テキスト文書とバイナリ添付ファイルを区別する。
- テキスト文書は原文を正本として保持する。
- ASTや構文木は文書形式・言語ごとの解析結果として扱う。
- ソース位置情報を保持する。
- 編集・閲覧・プレビューで共通の文書セッションを使用する。
- 文書形式固有の情報は拡張可能なメタデータとして保持する。
- 未対応の構文や情報を可能な限り保持する。
- 特定のAST構造をすべての文書に強制しない。

### 4.3 文書形式拡張

文書形式ごとの処理を独立したモジュールとして管理する。

担当機能：

- ファイル形式の識別
- 読み込み・書き込み
- 構文解析
- 文書構造の生成
- レンダリング情報の提供
- シンタックスハイライト
- エクスポート・インポート
- 文書形式固有の編集機能

Markdownは標準搭載する文書形式拡張とし、Markdown以外の形式も追加できる構造にする。

### 4.4 言語拡張との分離

文書形式拡張、プログラミング言語拡張、自然言語拡張を区別する。

- Document Format：Markdown、その他の文書形式。
- Programming Language：Rust、Python、JavaScriptなど。
- Natural Language：日本語、英語、中国語、アラビア語など。
- Language Server：LSPを通じたプログラミング言語機能。
- Parser：文書形式・言語の構文解析。
- Localization：アプリケーションUIの翻訳・地域化。

それぞれ独立して追加・変更・無効化できるようにする。

## 6. パーサーシステム

### 6.1 基本構成

パーサーはプラグインとは独立した拡張体系として管理する。

パーサーはネイティブ実装とWASM実装で共通の `parser-api` を使用し、ホスト側から呼び出す。標準搭載パーサーを含むすべてのパーサーをWASMモジュールとして実行する。各パーサーは独立したモジュールとし、互いに直接依存しない。パーサーの組み合わせ（第三者のパーサー拡張を含む）はホストを経由して実行時に行う。WASMランタイムの整備（Phase 6）まではネイティブで実装し、同じ方式で組み合わせる。詳細は [ADR-0004](adr/0004-markdown-parser.md)。

**Standard Markdown Parser**

- CommonMarkを基本とする標準Markdownパーサー。
- 標準搭載するコアパーサー。
- 標準Markdown構文の解析を担当する。
- Obsidian Markdown Parserなどの追加拡張の基盤となる。
- 独立モジュールとして無効化・交換可能にする。

**Obsidian Markdown Parser**

- 標準Markdownパーサーを拡張する追加パーサー。
- Obsidian固有のMarkdown構文と参照方式を実装する。
- 標準パーサーの構文認識・AST・文書モデルを利用する。
- 標準パーサーとは独立して有効・無効化できる。
- WASMモジュールとして提供する。WASMランタイムの整備（Phase 6）まではネイティブ実装で提供する。
- 第三者のパーサー拡張と同時に有効にできる。

**埋め込み言語パーサー**

- Markdownの中の別の言語で書かれた部分（LaTeXの数式、Mermaid、検索式、プログラミング言語のコードなど）を解析する。
- Markdownパーサーは別の言語の部分を埋め込み領域として識別するだけで、中身は言語ごとの独立したパーサーが解析する。
- 言語ごとに独立して有効・無効化できる。対応するパーサーが無い場合は原文の文字列として扱う。
- 要件は [`requirements/parser.md`](requirements/parser.md) §4 で管理する。

### 6.2 パーサー拡張API

- ブロック構文・インライン構文の拡張フック。
- AST変換・ノード登録。
- リンク解決・参照解決の拡張ポイント。
- 前処理・トークン解析・後処理。
- 拡張パーサーの実行順序と優先順位の管理。
- 構文競合の検出と処理。
- 共通文書モデルへの変換。
- 原文とソース位置情報の保持。
- 独立したAPIバージョニング。
- 構文機能（Feature）単位の宣言と、パーサー側の設定による個別のオン・オフ（[要件](requirements/parser.md) §1）。

### 6.3 Obsidian Markdown拡張

以下の構文・機能を独立した拡張として実装する。

- ブロック識別子
- ブロックリンク
- 見出しリンクの互換処理
- Wikilink
- 埋め込み構文
- コールアウト
- タグ
- プロパティ（YAMLフロントマターの型、`tags`・`aliases`・`cssclasses`）と別名
- ハイライト（`==text==`）
- コメント（`%%...%%`）
- インライン脚注（`^[...]`）
- タスクの任意の状態文字
- その他必要な独自構文

内部リンクの標準生成形式は相対パスのMarkdown Linkとする。

Wikilinkなどは互換性を確保するための追加構文として提供する。

Obsidian固有構文の対応範囲と構文機能の一覧は [`requirements/parser.md`](requirements/parser.md) で管理する。各構文はパーサー側の設定で個別にオン・オフできる。

### 6.4 パーサー実行

- 標準Markdownパーサーを含むすべてのパーサーをWASMモジュールとして実行する（ADR-0004）。
- メモリ・実行時間を制限する。
- パーサーの組み合わせと依存関係を管理する。
- 個別の有効・無効化に対応する。
- 拡張が利用できない場合は標準形式またはプレーンテキストにフォールバックする。
- パーサーの切り替えによって原文を破壊しない。

## 8. Markdown Link・内部リンク

### 8.1 基本方針

- 標準Markdownリンクを内部リンクの基本形式とする。
- Vault内のファイル参照には相対パスを使用する。
- パス区切りには `/` を使用する。
- URLエンコードしない。日本語・空白・記号はそのまま書き、CommonMarkの構文上必要な場合は山括弧の形式とバックスラッシュのエスケープを使う（[ADR-0009](adr/0009-link-anchor-format.md) §5）。
- リンクの表示文字列とリンク先を独立して管理する。
- Wikilink形式は標準リンク形式には使用せず、互換性拡張として扱う。

基本形式：

```markdown
[ノート名](./note.md)

[別フォルダのノート](../folder/note.md)

[画像](../assets/image.png)
```

### 8.2 リンク解決

- 相対パスはリンク元ファイルのディレクトリを基準に解決する。
- Vault境界を越える相対パスを禁止する。
- ファイル名変更・移動時に内部リンクを更新できるようにする。
- リンク先が存在しない場合もリンク情報を保持する。
- 未解決リンクを検出・表示する。
- 同名ファイルはパスによって一意に解決する。
- リンク候補の検索・補完に対応する。
- OS間のファイル名・パスの差異を考慮する。

### 8.3 見出しリンク

- Markdownアンカーによる見出し参照に対応する。
- アンカーは見出し文字列そのものとする（Obsidian方式。形式は [ADR-0009](adr/0009-link-anchor-format.md)）。
- 日本語見出しに対応する。
- 同名見出しの重複を処理する。
- 見出し名の変更時にリンクを再解決する。
- 見出し候補を一覧表示する。
- リンク先の見出しまで移動する。

### 8.4 ブロックリンク

Obsidian Markdown拡張として独自のブロック識別子・参照機能を提供する。

ブロック識別子：

```markdown
これは参照可能な段落です。 ^block-id
```

リンク：

```markdown
[対象の段落](./note.md#^block-id)
```

- `^block-id`形式の識別子を使用する。
- 識別子に使用できる文字はASCIIの英字・数字・ハイフンとする（Obsidian互換。[ADR-0009](adr/0009-link-anchor-format.md)）。
- 段落・リスト項目などを参照可能なブロックとして扱う。
- ブロックIDはノート内で一意に管理する。
- 手動指定と自動生成に対応する。
- 編集時に既存のIDを可能な限り維持する。
- IDの重複を検出・解決する。
- ブロック候補を検索・選択できるようにする。
- リンク先ブロックをプレビュー・表示できるようにする。

## 9. プログラミング言語拡張（Language Extension）

### 9.1 基本方針

プログラミング言語固有の定義や入力支援を独立した拡張として提供する。

アプリケーション本体は特定のプログラミング言語を前提としない。

### 9.2 言語定義

各Language Extensionは以下を定義できるようにする。

- 言語ID
- 表示名
- ファイル拡張子
- ファイル識別規則
- MIME Type
- シンタックスハイライト
- コメント記法
- インデント規則
- 括弧・引用符の設定
- 自動補完の基本設定
- 対応LSPサーバー
- 言語固有の設定

### 9.3 言語拡張の管理

- 言語ごとに独立して追加・削除・無効化できる。
- 複数の言語拡張を同時に利用できる。
- 同じファイル形式に複数の言語定義が競合する場合の優先順位を管理する。
- LSPとの連携は独立したLSP Extensionを通じて行う。

## 10. LSP Extension

### 10.1 基本方針

Language Server Protocol（LSP）を利用し、外部Language Serverから言語機能を提供する。

LSP対応は独立した拡張として管理し、Language Extensionやエディター本体に直接組み込まない。

### 10.2 対応機能

- コード補完
- 定義への移動
- 参照検索
- ホバー情報
- 診断情報
- エラー・警告表示
- コードアクション
- リネーム
- フォーマット
- シンボル検索
- セマンティックトークン
- インレイヒント
- シグネチャヘルプ

サーバーが対応する機能のみ有効化する。

### 10.3 LSP管理

- Language Serverの起動・停止・再起動。
- 初期化とCapability Negotiation。
- 文書同期。
- サーバーごとの設定。
- ワークスペース管理。
- 複数サーバーの管理。
- サーバーのログ・診断。
- バージョン・依存関係の管理。

### 10.4 実行方式

プラットフォームに応じて以下を利用できる構造とする。

- ローカルプロセス
- アプリケーション内蔵サーバー
- WASMなどのインタープリター実行環境
- リモートLanguage Server

モバイルでは任意のネイティブ実行ファイルを自由にダウンロード・実行できるとは限らないため、サーバーの同梱・組み込み・リモート接続も考慮する。

### 10.5 言語サーバーとの分離

- LSPクライアントは共通実装とする。
- 各言語のLanguage Serverは別途提供・管理する。
- 言語拡張は使用するLSPサーバーの情報を宣言できるようにする。
- LSP未対応言語でも基本的な編集機能を利用できるようにする。

## 11. MCP Extension

### 11.1 基本方針

Model Context Protocol（MCP）に対応する独立した拡張を提供する。

MCPはAIアプリケーションと外部ツール・データソースを接続するために使用する。

### 11.2 対応機能

MCP Clientとして以下に対応する。

- Tools
- Resources
- Resource Templates
- Prompts
- Roots
- Sampling
- Elicitation
- 対応する通知・サブスクリプション

実装する機能はプロトコルバージョンとCapabilityに基づいて管理する。

### 11.3 接続方式

- stdio
- Streamable HTTP

### 11.4 MCP管理

- 複数MCP Serverの登録・管理。
- サーバーごとの接続設定。
- 認証・認可。
- Capability Negotiation。
- 接続・切断・再接続。
- ツール・リソース・プロンプトの一覧管理。
- サーバーごとの有効・無効化。
- ログ・エラー管理。
- 接続先ごとの権限管理。

### 11.5 セキュリティ

- 外部ツールの実行はユーザーの権限設定に従う。
- 破壊的操作や外部へのデータ送信は明示的な確認を行う。
- サーバーごとにアクセス可能なVaultや文書を制限する。
- シークレットを必要な範囲でのみ提供する。
- 信頼できないサーバーの接続を制限できるようにする。

### 11.6 MCP Server機能

将来的にHisui Notes自体をMCP Serverとして公開できる構造を考慮する。

- Vaultの検索
- 文書の読み取り
- 許可された文書の編集
- メタデータ取得

MCP Client機能とは分離し、外部からの操作権限を個別に管理する。

## 12. ACP Extension

### 12.1 基本方針

Agent Client Protocol（ACP）に対応する独立した拡張を提供する。

エディターとAIエージェントの間の通信・セッション管理に使用する。

### 12.2 対応機能

- ACP Agentへの接続。
- セッション作成・再開。
- 会話の送受信。
- エージェントの進行状況の受信。
- ストリーミング表示。
- ツール実行状況の表示。
- 計画・状態変更の表示。
- ファイル変更情報の受信。
- キャンセル。
- 認証。
- 権限要求への応答。
- プロトコルバージョン・Capability Negotiation。

### 12.3 セッション管理

- 複数Agentの登録・管理。
- エージェントごとの接続設定。
- セッションの作成・再開・終了。
- セッション履歴。
- 実行状態・進行状況。
- エラー・ログ管理。
- エージェントごとの権限設定。

### 12.4 セキュリティ

- ファイル変更や外部操作の権限を管理する。

- 信頼できないAgentを隔離する。

### 12.5 MCPとの分離

- ACPはAI Agentとのセッション・操作連携を担当する。
- 両者の実装と設定を独立させる。
- AI Chatなどの上位機能から両方を利用できるようにする。
- 一方を無効化しても他方の機能に影響しないようにする。

## 18. 自然言語・国際化基盤（Internationalization）

### 18.1 基本方針

- 特定の自然言語・文字体系に依存しない設計とする。
- UIの多言語化と文書内容の多言語対応を独立して扱う。
- Unicodeを基本文字表現として採用する。
- 言語・地域・文字体系を識別する標準的な言語タグを使用する。
- 複数言語が混在する文書を扱えるようにする。
- 言語固有の処理を共通コアに直接組み込まず、国際化基盤と独立した言語拡張に委譲する。

### 18.2 UIローカライゼーション

- UI全体の多言語化に対応する。
- 翻訳リソースをアプリケーションコードから分離する。
- 翻訳の追加・変更を容易にする。
- 実行中の言語切り替えに対応する。
- 翻訳リソースのフォールバックに対応する。
- 複数形、性別、文法上の格など、自然言語ごとの表現差を扱えるようにする。
- コアプラグイン・ユーザープラグインも独自の翻訳リソースを提供できるようにする。
- 翻訳されていない項目は適切な優先言語にフォールバックする。

### 18.3 Locale Management

- BCP 47に基づく言語タグを使用する。
- 言語・文字体系・地域を区別する。
- ユーザーの優先言語リストを管理する。
- UI表示言語と地域別書式設定を独立して指定できるようにする。
- OSの言語設定を取得できるようにする。
- 言語・地域に応じたフォールバックを提供する。
- 日付、時刻、数値、通貨、カレンダー、週の開始日などを地域別に扱う。
- タイムゾーンと地域設定を区別する。

### 18.4 Unicode・テキスト処理

- Unicode文字列を正しく処理する。
- NFC・NFDなどのUnicode正規化に対応する。
- 原文を不必要に正規化・変換せず、原本を保持する。
- 書記素クラスタ単位のカーソル移動・選択・削除に対応する。
- 単語・文・行の境界を適切に判定する。
- 言語や書記体系に応じた文字列処理に対応する。
- 日本語・中国語・韓国語など、空白で単語を区切らない言語にも対応する。
- 絵文字・結合文字・異体字・サロゲートペアなどを正しく扱う。
- Unicodeのバイト位置、コードポイント位置、UTF-16位置、書記素クラスタ位置の変換を管理する。

### 18.5 テキスト描画・組版

- 複雑な文字体系のシェーピングに対応する。
- ラテン文字以外の文字体系を正しく描画する。
- アラビア文字・ヘブライ文字などの右から左への表示に対応する。
- 左右方向が混在する文章の描画に対応する。
- 言語・文字体系に応じたフォントフォールバックに対応する。
- 結合文字、合字、異体字、カラー絵文字などに対応する。
- 言語ごとの改行・禁則・行間処理に対応する。
- 必要に応じて縦書きなどの組版方式を追加できる構造にする。
- テキスト描画と文書原文の文字位置を対応付ける。

### 18.6 入力・IME

- 各OSのネイティブIMEを利用する。
- 日本語・中国語・韓国語などの変換入力に対応する。
- 変換中テキストと確定済みテキストを区別する。
- 合成中の文字列とカーソル位置を正しく管理する。
- ハードウェアキーボードとソフトウェアキーボードに対応する。
- 入力言語の切り替えを妨げない。
- モバイルのIMEとテキスト編集機能の連携を保証する。
- 右から左への入力や複合文字入力にも対応する。

### 18.7 検索・並べ替え

- Unicode正規化を考慮した検索に対応する。
- 言語・地域に応じた文字列比較と並べ替えに対応する。
- 大文字・小文字、アクセント、文字体系に応じた検索オプションを提供する。
- 日本語・中国語・タイ語などに適した検索用文字列分割に対応する。
- 必要に応じて言語別の形態素解析・トークナイザーを追加可能にする。
- 元の文書内容と検索用インデックスを分離する。
- 検索用の正規化・変換で原文を変更しない。

### 18.8 自然言語拡張

プログラミング言語向けのLanguage Extensionとは独立した拡張体系とする。

追加可能な機能：

- 言語別スペルチェック
- 文法チェック
- 文章校正
- 形態素解析
- 単語分割
- 翻訳支援
- 文字変換・表記変換
- 言語判定
- 言語別入力支援
- 読みや発音の補助
- 文章構造の解析

各機能は独立して追加・無効化できるようにする。

### 18.9 文書の言語情報

- 文書単位で主要言語を指定可能にする。
- 必要に応じて段落・ブロック単位の言語情報を保持できるようにする。
- 複数言語が混在する文書を許容する。
- 文書の言語とアプリケーションの表示言語を独立して管理する。
- 言語情報を検索・校正・組版などの拡張機能から利用できるようにする。
- 言語が未指定の場合は自動判定に依存せず、適切な標準動作を行う。

### 18.10 推奨技術

- ICU4X：国際化処理・Locale・日付・数値・並べ替え・文字列処理。
- Project Fluent / fluent-rs：UIローカライゼーション。
- Unicode Standard：文字処理・双方向テキスト・正規化・文字境界。
- OSネイティブIME：各プラットフォームの入力・変換処理。
- テキストシェーピング・組版ライブラリ：複雑な文字体系の描画。

技術選定時には、GPUIの既存テキスト描画基盤との互換性を検証する。

## 19. ユーザープラグイン・拡張管理

### 19.1 基本方針

- ユーザープラグインはWASMを基本実行形式とする。
- Lazy Loadingに対応する。
- コマンド、イベント、UI要素、文書処理機能を登録できる。
- 対応プラットフォームを宣言できる。
- 必要なCapabilityを宣言する。
- 個別の有効・無効化に対応する。
- 更新・削除時にデータを保護する。

### 19.2 拡張の分類

- Core Features：アプリケーションの基本基盤。
- Core Plugins：標準搭載の追加機能。
- User Plugins：ユーザーが追加する一般機能。
- Parser Extensions：文書形式・構文解析の拡張。
- Language Extensions：プログラミング言語の定義・入力支援。
- Natural Language Extensions：自然言語別の処理・文章支援。
- LSP Extension：Language Server Protocol連携。
- MCP Extension：Model Context Protocol連携。
- ACP Extension：Agent Client Protocol連携。
- Snippet Extension：テンプレート・スニペット機能。
- Theme Extensions：テーマ・外観の拡張。

各拡張体系はそれぞれ独立したAPI・設定・ライフサイクルを持つ。

共通の拡張管理基盤を利用するが、すべてを単一のプラグインAPIに無理に統合しない。

### 19.3 拡張の実行方式

- 一般的なユーザープラグインとパーサーはWASMを基本とする。
- OS機能やプロセス管理を必要とする拡張には、権限制御されたホストサービスを提供する。
- LSP・MCP・ACPの通信部分は独立したホスト側モジュールとして実装する。
- プロトコル接続先やLanguage Serverは必要に応じてネイティブプロセス・リモート接続を利用する。
- 実行方式と配布形式を混同しない。
- モバイルの実行制約とアプリストア規約を考慮する。

### 19.4 プラグイン互換性

**Universal Plugin**
- 全プラットフォームで同一のWASMバイナリ・機能を提供する。

**Conditional Plugin**
- OS機能などの利用可否によって機能が変化する。

**Platform Plugin**
- 特定OS向けの機能やUIアダプターを必要とする。

## 25. 最終設計原則

Hisui Notesは特定の文書形式、プログラミング言語、自然言語に依存しない、モジュール式の文書編集アプリケーションとする。

アプリケーションコアは文書・データ・編集状態・拡張機構の整合性を保証し、GPUIは全プラットフォーム共通のUIフレームワークとして使用する。

UIはモジュール式とし、コア機能・コアプラグイン・ユーザープラグインが独立したUI要素を登録できるようにする。

コアプラグインは標準搭載する追加機能を提供し、ユーザープラグインはユーザーによる機能拡張を担当する。

パーサー、文書形式、プログラミング言語、自然言語、LSP、MCP、ACP、Snippet、テーマはそれぞれ独立した拡張体系とする。共通の拡張管理基盤を利用しながら、各々の責務とAPIを分離する。

Markdownは標準搭載する文書形式の一つとして扱い、標準MarkdownパーサーとObsidian Markdown拡張を提供する。

AI Chat UIはコアプラグインとして標準提供し、AIプロバイダー、MCP、ACPなどの接続先を独立して追加・変更できるようにする。

自然言語の多言語対応を基本機能とし、UI翻訳だけでなく、Unicode、IME、複雑な文字体系の描画、双方向テキスト、検索・並べ替えまで扱える基盤を整備する。

WASMをパーサー・ユーザープラグインの共通実行形式とし、ホストAPIを介して安全に機能を利用できる構造にする。

デスクトップとモバイルで共通のUI・データモデル・拡張機構を維持しながら、各プラットフォームに適した操作体験を提供する。

拡張性を確保するためにコアを過度に複雑化せず、データの安全性、編集性能、国際化、保守性を優先する。
